## 已确认的产品约束

以下约束来自用户的明确要求或选择；其下字段、接口和技术实现已在完整推荐方案中展开，供整体审阅后调整。

| 编号 | 已确认内容 |
|---|---|
| BASE-01 | CMDB 与 Pipeline 是两个模块，后端使用 Go 与 Gin，并置于不同 Git 仓库；前端共用一个仓库 |
| BASE-02 | 首期为 Next.js 与 React Web 控制台 |
| BASE-03 | 数据库使用MySQL；本次推荐8.4 LTS、GORM MySQL驱动和goose迁移，确切patch在实施时锁定 |
| BASE-04 | 空间统一管理成员和权限；空间下有子系统，子系统下有长期存在的应用，应用关联流水线 |
| BASE-05 | 发布版本归属空间，通过关联关系收集应用，首期汇总交付情况，各应用独立运行 |
| BASE-06 | CMDB 管理应用交付所需信息，作为 Pipeline 的元数据来源 |
| BASE-07 | 流水线可编辑，可添加 Stage 与 Job；Stage 串行，同 Stage 的 Job 并行 |
| BASE-08 | Job 是平台定义的原子能力，由管理员编写并发布模板，用户从 Job 市场选择 |
| BASE-09 | Job 可自动或手动触发；自动 Job 正常启动，手动 Job 独立等待，全部成功后进入下一 Stage |
| BASE-10 | Jenkins 作为底层执行器，流水线编排与管理由平台负责 |
| BASE-11 | 首期使用本地账号，真实交付场景为构建镜像并部署到 Kubernetes |
| BASE-12 | 先细分需求并形成方案文档，再逐项实现；现已授权先完成全部推荐方案后集中审阅 |
| BASE-13 | 代码按业务组织，轻量分工，简单、可读和容易维护优先 |
| BASE-14 | 数据访问使用 GORM，复杂调度使用显式 SQL |
| BASE-15 | 永远不写兼容性代码，只维护当前确认的正确方案；替换时同步更新关联链路并删除旧实现 |
| BASE-16 | CMDB 分 identity、space、application、release；Pipeline 分 catalog、definition、execution，流水线管理与配置同属 definition |
| BASE-17 | 首期 Pipeline API 与 Worker 分进程部署，共用一个后端仓库和业务实现 |
| BASE-21 | 启动时手工创建并传入需要的依赖，不引入依赖注入工具，也不强制建立 bootstrap 包 |
| BASE-22 | 架构讨论首先聚焦代码风格、可读性和可维护性；按真实需要分层与抽象，不整复杂 |

2026-10-16：根据用户澄清，撤回此前强制 public 契约、外置查询层、UnitOfWork/TxStores 和最小端口拆分的要求。它们不再作为当前代码约束；技术栈、业务范围和 API/Worker 分进程部署选择保留。

## 单项需求的推进方式

```text
待讨论 → 讨论中 → 已确认 → 实现中 → 待验收 → 已验收
```

“已确认”需要记录明确的用户结论或用户授权采用建议的上下文；没有答复时保留“讨论中”。“待验收”表示实现及开发者自检完成，不等同于用户已验收。

按用户最新授权，本次一次生成全部推荐方案，不等待每条单独回复。后续修改可按需求ID或页面聚焦讨论，记录问题、用户场景、规则、交互、数据/API、失败边界与验收；不能用目录结构替代功能设计，也不能用实施清单替代产品结论。

文档和讨论的复杂度与实际问题相称。简单需求用几段写清即可；不为每个接口、函数和目录设计独立评审，也不把常规编码事项反复做成选择题。

需求确认后拆出对应实现任务，任务引用需求 ID。实现发现新的业务选择时回到该需求记录，不在代码里静默更改已确认结论。结论变化保留简短的变更原因及影响，正文只保留当前有效方案，历史记录明确标为已替代。

## 工程硬约束

已确认不写兼容性代码：不保留旧字段别名、旧协议解释器、旧实现回退或新旧双读双写。跨仓库改动协同更新；存量格式显式迁移；不支持的输入明确拒绝。业务历史与原始快照按要求保留，不等于保留旧引擎。完整边界见 [工程约束](engineering-constraints.md)，执行规则见 [AGENTS.md](../AGENTS.md)。

## 现有技术草案的处理

`pipeline-orchestration-design.md` 现为编排设计导航，examples、schemas与完整推荐方案同步。应用环境互斥、人工等待占槽、失败收敛、digest部署、重跑和保留/超时均已在design目录给出推荐值，集中见重点取舍；它们仍允许用户整体审阅后修改。

API 与 Worker 首期分进程部署已确认，原合并进程建议不再采用。其余尚未确认的需求不得因为已有示例或 Schema 就被当作产品限制。

当前目录暂存系统级设计；确认仓库边界并开始实现后，服务专属文档随对应仓库维护，系统级需求总表指定单一维护位置，不复制出多份互相冲突的结论。
