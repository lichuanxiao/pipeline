# ARCH-01 代码风格可读性与可维护性

状态：本文件保留简单代码示例与解释，完整推荐基线见 [工程规范 ARCH-01](../../design/01-engineering.md#arch-01-代码风格与可维护性)。用户已授权全项按推荐方案写全后集中审阅；此前强制多层目录、public契约与事务框架的要求已撤回。

## 目标

让接手的人容易找到功能、顺着读懂流程、看清数据在哪里修改，并且修改一项需求不需要同时改很多纯转发文件。

保留业务模块组织与 API/Worker 分进程部署。代码按实际需要拆分，目录不承担强制架构仪式。

## 代码规则

| 方面 | 做法 |
|---|---|
| 命名 | 名字准确表达业务，避免无上下文的 Process、HandleData、Manager 和不断膨胀的 utils |
| 函数 | 一个函数完成一件能清楚描述的事，错误尽早返回，让正常流程顺着读；不按固定行数机械拆函数 |
| 文件 | 相关代码放在一起，按实际职责拆文件；不为只有一句转发的逻辑单建一层 |
| 注释 | 解释业务原因、状态约束和非直观取舍，不逐行复述代码 |
| 错误 | 影响结果的错误必须处理，返回时补充操作背景；不吞错、不伪造成功、不在多层重复记录同一错误 |
| 参数 | 使用明确类型和名称；参数变多且确实属于同一业务输入时再合并结构体，不用任意 map 贯穿所有函数 |
| 数据结构 | 字段含义相同时允许复用；接口暴露范围不同、需要校验或脱敏时再定义请求响应结构，不默认复制四套模型 |
| 复用 | 有真实重复或稳定的共性再提取；不为未来可能需要的能力预建框架 |
| 数据修改 | 关键状态变化集中在容易找到的位置，条件检查和修改关系清楚 |
| 格式 | Go 统一 gofmt，前端统一格式化和 lint 配置，不靠人工讨论缩进 |

Go 命名、格式和评审习惯参考 [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)；本表中的业务组织方式是项目规范建议。

## 用具体写法讨论规范

本轮先评审命名、函数组织、错误与日志这几项，不扩展代码框架。下面只展示手动触发的主流程写法，相关类型和方法尚未实现；完整权限、幂等和并发规则在 RUN-03 确认。

```go
func (s *Service) TriggerManualJob(ctx context.Context, spaceID, jobRunID string) error {
    jobRun, err := s.findJobRun(ctx, spaceID, jobRunID)
    if err != nil {
        return fmt.Errorf("load job run %s: %w", jobRunID, err)
    }

    if jobRun.Status != JobWaitingManual {
        return ErrJobNotWaiting
    }

    if err := s.enqueueManualJob(ctx, jobRun); err != nil {
        return fmt.Errorf("enqueue job run %s: %w", jobRunID, err)
    }
    return nil
}
```

这个例子要表达的写法是：

1. 名字说明动作和对象。TriggerManualJob 表示人工放行，jobRun 表示一次执行，避免与 Job 模板混用；缩写统一写成 ID、URL 等常见形式。
2. 先处理错误和不满足条件的情况，正常流程保持直接，不使用多层 if/else 包裹主要动作。
3. findJobRun 负责按空间定位记录并处理未找到等结果；enqueueManualJob 在事务中复核 Run 与 Job 的当前状态，原子保存状态变化和待处理工作。它们有真实职责，仍可放在同一个模块的少量文件里。
4. 示例中的首次状态判断用于直接反馈；入队函数必须再次保护并检查状态，不能把事务外检查当作并发保证。入队不直接调用 Jenkins。
5. 返回错误时使用 %w 保留原因，业务上可识别的错误使用明确值，通过 errors.Is 等方式判断，不比较错误字符串。

小功能可以把必要操作直接写在一个函数中；示例不要求所有流程都拆成相同数量的函数。

### 错误和日志的具体约定建议

- 查询失败不能继续返回空结果冒充成功；资源不存在和系统故障应能区分。
- 普通业务失败通过 error 返回，不用 panic 代替校验。
- 内部错误补充“正在做什么”和必要的资源 ID，不把密钥或完整敏感请求写进错误。
- 一般由 API 或 Worker 入口记录一次最终失败，内部函数返回错误；关键业务事件可以单独记录，不在每层重复打印同一错误。
- 仅在需要解释原因时写注释，例如为何要在事务内再次检查状态，不注释“调用查询”“返回成功”等直观代码。

当前这些具体写法仍是评审建议，未因写入示例而视为业务实现或已确认规范。

## 简单组织示例

```text
cmd/
  api/main.go
  worker/main.go
internal/
  config/
  database/
  modules/
    definition/
      handler.go       # HTTP 参数与响应
      service.go       # 业务流程
      repository.go    # 需要集中管理的 SQL，按需添加
      model.go         # 数据结构
      dto.go           # 请求响应结构，按需添加
      service_test.go  # 关键行为测试
    catalog/
    execution/
  jenkins/client.go
  cmdb/client.go
```

这是示意，不是每个模块必须创建的文件清单。一个小功能可以先放在少量文件里，代码增长后再按职责拆分。

Handler 处理请求和响应，Service 写清业务流程。简单的数据操作可以直接用 GORM；复杂、重复或需要统一管理的 SQL 再集中到 repository.go。Repository 可以是普通函数或具体结构体，不强制先写接口。

Jenkins、CMDB 请求集中在各自 client 中，业务代码调用清楚的方法即可。不额外建立 domain、application、adapters、public、组合查询框架或多层 DTO 转换。

模块之间通过普通方法协作，保持职责清楚并避免循环依赖。简单只读列表可以在同服务的仓储中联查必要数据，不为每个列表创建协调层；CMDB 与 Pipeline 之间仍通过 API 交互，不跨服务查询业务库。

## 可维护性要求

- 修改一个字段时，检查受影响的真实调用点，不保留旧别名或兼容分支。
- 业务状态使用明确常量，规则集中表达，避免同一规则在多个入口重复。
- 时间、超时、凭据等来源明确，不散落硬编码，不把依赖藏在任意 context 值中。
- 先用普通函数和结构体；真实测试、替换或复用需要出现后再提取接口。
- 事务使用 GORM 的显式事务，具体规则见 [ARCH-02](ARCH-02-persistence.md)。
- API 和 Worker 共用业务代码，各自启动，不复制一套业务实现。

## 前端同样保持直接

组件按实际职责拆分，状态尽量放在使用它的位置。出现真实复用再提取共享组件或 Hook，不为每段逻辑套 Hook，不为所有表单引入全局状态。接口类型明确，加载、失败与成功状态容易看懂。

## 代码评审关注点

读代码时能否快速回答：入口在哪里、主要流程是什么、数据在哪里改、失败时会怎样、修改需求会影响哪些位置。

测试优先覆盖业务判断、状态变化、失败处理、事务与并发；不为纯转发层或简单取值代码堆测试。具体工具在 ARCH-06 确定。
